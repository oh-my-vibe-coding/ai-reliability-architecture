# 维护系统 · README

> [← 返回目录](../README.md)

本书维护三类内容：**事实与实现、工作范式、核心论断与理念**。除了更新模型、价格和接口，还要检查读者怎样组织任务、怎样与 AI 协作，以及书中的建议为什么仍然成立。

月度扫描、季度审查、年度重审提供排期。已确认的错误或高影响变化随发现随处理；没有足够证据时记录待验证，不为维持更新频率而改写结论。

---

## 维护对象

| 层次 | 主要检查 | 主要产出 |
|---|---|---|
| 事实与实现 | 型号、价格、API、工具、法规与案例来源 | 可核验快照、勘误和兼容说明 |
| 工作范式 | 委托单位、上下文、长任务、协作、验证与恢复 | 有适用边界的方法、架构与练习修订 |
| 核心论断与理念 | 职责、学习、判断、信任等主张的前提与反例 | 保留、限定、改写或撤回的理由 |

第三层也要区分事实判断、工程建议和价值选择。它们需要的证据与讨论不同；具体流程见[范式与理念审查](范式与理念审查.md)。

## 基本节奏

```text
月度：核验快变事实，同时收集范式与理念变化信号
季度：选择高影响候选，核查反例和证据，抽查核心论断
年度：重审读者、职责边界、主线与训练目标
事件触发：发现已证实错误、危险建议或关键前提失效时及时处理
```

每次都留下核验范围、未完成项、决定和后续动作。完整修订需要多少时间，取决于调研、实验和跨章同步；原有的 15-20 分钟月扫、约 2 小时季审只能作为起步安排，不能承诺覆盖全部工作。

维护可以复用 B1 的预测核对、B2 的论证评审、B3 的独立研究，见[第 18 章](../练习/10-三个核心训练动作.md)。这些是学习方法，不限定所有维护工作必须手工完成。

## 漂移度表示复查优先级，不表示结论可信度

| 标记 | 类型 | 默认安排 |
|---|---|---|
| 🧱 | 基础内容、预期变动较少 | 年度复查；季度抽查主张；失效信号随时触发 |
| 🔩 | 方法与实现缓变 | 季度复查，并跟随具体依赖变更 |
| 📊 | 快变事实与实践 | 月度扫描，按影响决定核验与修改 |
| 🕒 | 高时效快照 | 查日期与来源，不自动视为当前结论 |

"基石"不等于永真，也不只检查型号。数学关系有前提，学习方法要看效果，组织和职责主张有适用条件。详见[漂移度表](漂移度表.md)。

## 版本号约定

本书沿用 MAJOR.MINOR.PATCH，按实际影响选择：

- **Patch**：事实勘误、快照与兼容更新、收紧不准确表述，未改变整体阅读和实践路径。
- **Minor**：新增方法或配套章节、有实质影响的实践修订，原路径仍可延续。
- **Major**：核心主张、职责框架或学习路径发生实质重构，老读者需要迁移说明。

月检不必发 patch，季审不必发 minor，年审也不必发 major。整章编辑或新增一个术语本身不足以决定版本。

**当前已发布版本**：`v1.16.0` · 2026-10-18。工作中的修改先进入 Unreleased，发布时再统一版本。

发布需同步主 README、维护 README、CHANGELOG、站点版本 / 页脚，以及使用这些元数据的构建产物。正文实际变化时才更新该文件的 `updated`；检查过但没改，不伪装为内容更新。

## 协作与责任

团队按章节或主题指定维护者。AI 可以收集资料、找反例、起草，并在明确授权范围内直接修订文件；维护者需要核实关键证据，对纳入决定及发布负责。不要把多轮 AI 自评当成独立来源。

涉及核心论断或跨章方法的变更，应将证据、反方意见和迁移影响交给其他维护者复核。个人维护时，可以先发布有边界的修订并明确审查限制；不能虚构第二人 review 或未执行的实验。

一次维护是否有效，看它是否消除了已知错误、明确了适用边界并改进了读者决策。发现原文仍成立、决定暂不修改，也可以是有依据的审查结果。
