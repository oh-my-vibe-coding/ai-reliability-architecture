# 贯穿部署线 · H20 上的 Qwen3.8-27B 推理服务

> 所属：第四部分 · 训练与落地  ·  [← 返回目录](../README.md)

一句话：这条线带你**亲手把 Qwen3.8-27B 部署上一台 H20、跑成推理服务**，并通过部署和使用它的全过程，把缓存、TTFT、prefill、KV cache 这些名词一个个**用自己看到的数字钉进脑子**。

它与[贯穿项目 · SRE 事故助手](贯穿项目-SRE事故助手.md)互补：那条造"应用层"（RAG / agent / eval / SLO），这条造"底座层"（serving / 缓存 / 量化 / 容量）。两条线在"本地 vLLM 端点"处接上。

> [!IMPORTANT]
> 本线需要 **H20 × 1（96 GB HBM3，云或实体皆可）**。没有 H20 也能读，见[没有 H20 也能读](#没有-h20-也能读)。
>
> 本线是**可选平行线**，不挤占 19 周主线。建议在 Unit 0 和 Unit 3 附近各做一轮（见[周循环总览](周循环总览.md)），全部做完约 2-3 个周末。

## 案例配置块（单一事实源）

> 快照日期 **2026-08-23**。全书提到这个案例，都指向本块，不另写数字。**模型 / 引擎换代只改本块和版本记录，不碰其它章节**。

| 项 | 值 |
|---|---|
| 场景 | 内部客服 Copilot 的自托管推理（示意数字，量级真实） |
| 模型 | `Qwen/Qwen3.8-27B`（dense，2026-08-14 开源；bf16 权重 ≈ 54 GB）。型号出处见[深入 03 · §3.8](../深入/03-模型与工具场景化最佳实践.md) |
| 硬件 | H20 × 1（96 GB HBM3）。算力 / 带宽标定以[深入 01 · §3.3](../深入/01-首包延迟与吞吐的影响因素.md)为唯一来源，本块不复制 |
| 引擎 | vLLM V1（或 SGLang）；以下命令以 vLLM 为准 |
| 量化 | bf16 起步；Stage 5 之后按实测决定是否降到 FP8 / AWQ int4 |
| 并发 / 吞吐 | 故意不钉死——由 Stage 6 按你的显存算出来，这是教学点 |
| 版本记录 | 模型 / 引擎换代在此追加，详见 Stage 7 |

**为什么是 H20 + Qwen3.8-27B**：H20 算力只有 H100 的约 1/6.7、带宽反而更高（[深入 01](../深入/01-首包延迟与吞吐的影响因素.md) 的 §3.3 / §4.2 / §5），正好把"prefill 卡算力、decode 卡带宽"逼到极端；27B dense 是单卡装得下的典型自托管档。**选这个组合，等于把这本书最核心的一条原理搬到你桌上。**

## Stage 0 · 起步：把服务跑起来

**名词**：serving 栈、模型装载、显存占用、OpenAI 兼容端点。

**实验**：起服务。

```bash
pip install vllm   # 2026-08 快照：以当时最新稳定版为准
vllm serve Qwen/Qwen3.8-27B --gpu-memory-utilization 0.90
```

等日志出现 `Uvicorn running on http://0.0.0.0:8000`，另开一个终端：

```bash
curl http://localhost:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"Qwen/Qwen3.8-27B","messages":[{"role":"user","content":"你好，介绍一下你自己"}]}'
```

**观察**：

- `nvidia-smi`：约 54 GB 权重吃进显存，剩余留给 KV cache 与激活（Stage 3 的主角）
- 第一次请求比后续略慢（权重页缓存 / CUDA 图预热）
- 返回的是 OpenAI 兼容接口的 JSON——可用 OpenAI SDK 接入已支持的端点；具体参数、工具调用和流式行为仍需做兼容性验证

**反直觉点**：部署一个模型不是终点。从这一刻起，你是在运维一台**每秒吐 token 的机器**，不是"跑起来一个 demo"。

## Stage 1 · prefill 与 TTFT

**名词**：prefill、TTFT、TPOT、流式（streaming）。

**实验**：用 [measure_ttft.py](../代码/贯穿部署/measure_ttft.py)，同一个问题分别塞 100 / 1k / 4k token 的 system prompt，各发 3 次，记 TTFT 与 token 间隔：

```bash
python measure_ttft.py --base-url http://localhost:8000/v1 \
  --model Qwen/Qwen3.8-27B --input-lens 100 1000 4000 --repeat 3
```

**观察**：

- TTFT 随输入长度几乎线性上升——**prefill 是计算阶段，输入越长越贵**
- 首 token 之后的间隔（TPOT）基本不变——decode 每步读的是同一份权重
- 对照[深入 01 · §3.3](../深入/01-首包延迟与吞吐的影响因素.md)：它纸上算的 Qwen2.5-32B 8k 输入 ≈ 3.5 s，和你实测的 Qwen3.8-27B 同量级

**反直觉点**：模型"开口"多快和"说话"多快是两回事，SLO 要分开定——这正是[第 5 章](../知识/05-AI推理服务的可靠性工程.md)延迟类 SLI 分开测的原因。

---

## Stage 2 · decode 与并发

**名词**：decode、TPOT、连续批处理（continuous batching）、吞吐-延迟权衡。

**实验**：用 [bench_concurrency.py](../代码/贯穿部署/bench_concurrency.py) 跑 1 / 4 / 8 / 16 路并发：

```bash
python bench_concurrency.py --base-url http://localhost:8000/v1 \
  --model Qwen/Qwen3.8-27B --concurrency 1 4 8 16 --max-tokens 256
```

**观察**：

- 单路 decode 速度接近理论上限 74 tokens/s（带宽 4.0 TB/s ÷ 54 GB 权重，对应 TPOT 下限 ≈ 13.5 ms/token；[深入 01 · §4.2](../深入/01-首包延迟与吞吐的影响因素.md)）
- 并发升上去：单请求 TPOT 变差、**聚合** tokens/s 爬升——连续批处理让权重每步只读一次、被整个 batch 共享
- 把"并发 × TPOT × 聚合吞吐"画成一条曲线，这就是容量规划的原始数据

**反直觉点**：并发上去吞吐涨、延迟跌，两者不是"都要最好"。SRE 的工作是给这条曲线定一个**可接受的工作点**。

---

## Stage 3 · 显存与 KV cache

**名词**：KV cache、`--max-num-seqs`、显存利用率的 OOM 边界。

**实验**：边跑 Stage 2 的并发，边看 KV 块用量：

```bash
curl -s http://localhost:8000/metrics | grep -E "vllm:num_(free|used)_blocks"
```

再把 `--max-num-seqs` 从默认往上抬，看显存在哪个并发上打爆、vLLM 开始拒绝请求或 preempt。

**观察**：

- KV 块随"并发 × 上下文长度"线性增长。用[深入 05 · §2](../深入/05-LLM推理服务的容量规划.md) 的公式，把模型的 `num_hidden_layers / num_key_value_heads / head_dim` 从 config.json 代入精算
- 权重是**固定成本**，KV cache 是**随负载浮动的成本**——它才是显存规划的主角

**反直觉点**：H20 有 96 GB 显存还是会 OOM？因为 54 GB 权重只是底账，KV cache 按并发和上下文实时涨，`--gpu-memory-utilization` 给的余量就是用来吸收它的。

---

## Stage 4 · 缓存：prefix caching

**名词**：前缀缓存、命中率、TTFT 断崖。

**实验**：V1 引擎默认开启前缀缓存，重启确认后跑实验：

```bash
vllm serve Qwen/Qwen3.8-27B --enable-prefix-caching
python prefix_cache_hit.py --base-url http://localhost:8000/v1 \
  --model Qwen/Qwen3.8-27B --prefix-len 2000 --rounds 6
```

脚本发同一个长 system 前缀、每次换一个 user 尾巴，比较第 1 次 vs 第 2+ 次的 TTFT。

**观察**：

- 第 2 次开始 TTFT 断崖下降——命中的前缀不再重复 prefill
- `/metrics` 里 `vllm:prefix_cache_hit_rate` 上升
- 对照[深入 02 · §6.2](../深入/02-Prompt-Caching原理.md)：托管 API 的 prompt caching 和自建的 prefix caching 是**同一机制的两层实现**

**反直觉点**：缓存命不命中，请求都"成功"——TTFT 见分晓。这就是[深入 02 · §6.4](../深入/02-Prompt-Caching原理.md) 讲的"失效的静默性"：命中率掉下去时没有报警，只有 TTFT 悄悄变长。

---

## Stage 5 · 量化：容量换质量

**名词**：量化、FP8 / AWQ int4、静默降级。

**实验**：起三个实例，各用一档精度：

```bash
# bf16（默认）
vllm serve Qwen/Qwen3.8-27B --port 8001
# FP8（Hopper 原生）
vllm serve Qwen/Qwen3.8-27B --port 8002 --quantization fp8
# AWQ int4（需 AWQ 权重，如 Qwen/Qwen3.8-27B-AWQ）
vllm serve Qwen/Qwen3.8-27B-AWQ --port 8003 --quantization awq
```

用 [quant_compare.py](../代码/贯穿部署/quant_compare.py) 对同一组 prompt 跑三个端点，记录 TTFT / TPOT / 显存 / 结构化输出是否出错。

**观察**：

- 显存：int4 权重只有 bf16 的约 1/4，KV 池随之变大
- 质量：**整体看着没差，但结构化输出 / 长 context 可能悄悄掉分**——对应[科学 03 · §5.1](../科学/03-Quantization为什么有时坏.md) 的症状谱
- 延迟：小 batch 下量化省得有限，甚至可能更慢（反量化开销）

**反直觉点**：量化省的是**显存和带宽**，不是"一定省延迟"；质量代价是**分桶的**，不是均摊的。用[科学 03 · §5.2](../科学/03-Quantization为什么有时坏.md) 的验证清单逐类测，别只看整体 eval。

## Stage 6 · 收口：容量数学与 SLO

**名词**：并发上限、SLI / SLO、压测验证。

**实验**：

1. 算并发上限：

   - 可用显存 ≈ 0.90 × 96 ≈ **86 GB**
   - 权重 54 GB，KV + 激活余量 ≈ **30 GB**
   - 每 token KV ≈ 0.2 MB 量级（用[深入 05 · §2](../深入/05-LLM推理服务的容量规划.md) 公式按你的 config.json 精算）
   - 30 GB ÷ 0.2 MB ≈ 15 万 token 并发 KV，平均 2k context 约 **75 并发**

2. 定 SLO：TTFT p95 < 3 s（H20 prefill 慢，别按 H100 的手感定）；TPOT p90 ≤ 50 ms/token（按请求统计时，对应生成速度 p10 ≥ 20 tokens/s）
3. 用 `bench_concurrency.py` 压到 75 并发，验证 p95 是否达标

**观察**：纸上算的和压测的差距，就是预留余量与现实的差距。把差记下来，它就是下次规划的"折扣系数"。

**反直觉点**：并发上限不是 QPS 的函数，是"并发 × 上下文长度"的函数——[第 5 章](../知识/05-AI推理服务的可靠性工程.md)容量三角图的实测版。

## Stage 7 · 变更：换型与回滚

**名词**：灰度、回滚、模型版本、漂移。

**实验**：

1. 起第二个实例跑上一代 `Qwen/Qwen3.6-27B`，用 [05-llm-gateway.py](../代码/05-llm-gateway.py) 当网关做 A/B
2. 对比 TTFT / TPOT / 结构化输出通过率
3. 把流量切到新版本，出问题就切回来——**亲手演练一次回滚**，别等事故当天第一次做

**观察**：换模型 = 换一台新机器上线，要走和任何发布一样的流程（[深入 15](../深入/15-模型注册表与上线流程.md) 的 model registry 纪律）。

**反直觉点**：配置块里"模型"这一行是**全案例漂移最快**的一行。它变了，别的章节不用动——因为全书引用的是机制，不是型号。

## Stage 8 · 进阶（可选）：PD 分离

**名词**：PD 解耦、goodput、TTFT 稳定性。

**内容**：高并发 + 长输入下，H20 的 prefill 会成为 TTFT 的硬瓶颈。PD 分离把 prefill 和 decode 放到两个独立 GPU 池，各用合适的硬件。本线不要求做，读到[深入 20 · §4](../深入/20-单卡装不下的大模型分布式推理.md) 时回来对照：你现在 Stage 6 算出的"并发上限"，在 PD 分离下会被重写成 prefill 和 decode 两本账。

**观察**：至少理解一件事——TTFT 和 TPOT 卡两种资源、走两条扩容路径。这也是[第 5 章](../知识/05-AI推理服务的可靠性工程.md)把它们分成两类 SLI 的原因。

## 没有 H20 也能读

这条线的多数读者其实没有 H20——这没关系。每个 Stage 的「实验」都能降级成「纸上实验」：**现象的形状一样，只是把「跑脚本量」换成「对着锚点章节算」**。

- **降级对照（没卡 → 读哪章算）**：Stage 1 的 TTFT 实测 → [深入 01 · §3.3](../深入/01-首包延迟与吞吐的影响因素.md)「算一笔」的 3.5 s，把它当你的实测值；Stage 2 的 74 tokens/s → 用 §4.2 的「带宽 ÷ 模型字节数」自己算一遍；Stage 3 的 KV 增长 → 用 [深入 05 · §2](../深入/05-LLM推理服务的容量规划.md) 公式代一个 8B 模型的 config；Stage 6 的容量账 → 跟着 [深入 05 · §7](../深入/05-LLM推理服务的容量规划.md) 的 worked example 走一遍（那是 70B 的完整版）。Stage 4 / 5 / 7 分别对照 [深入 02](../深入/02-Prompt-Caching原理.md)、[科学 03](../科学/03-Quantization为什么有时坏.md)、[深入 15](../深入/15-模型注册表与上线流程.md) 的机制。
- **有 ≥ 24 GB 卡想真跑**：换 7B / 8B 级模型（如 [深入 05 · §2](../深入/05-LLM推理服务的容量规划.md) 表里的 Llama 3 8B），现象形状不变，只需改几个数——模型名、权重 54 GB → ~14 GB、KV 0.2 MB → 0.13 MB。**公式全部不变**：74 tokens/s 那步是「带宽 ÷ 模型字节数」，照代即可。

## 防漂移纪律

- **锚点 = 机制与现象**（TTFT 随输入长、decode 卡带宽、KV 吃显存、前缀命中、量化分桶掉分）——不变
- **实例 = 型号与版本**（qwen3.8-27b、vLLM 版本）——可换
- 换型只改配置块 + 版本记录，全书其它地方引用机制，不用动
- 沿用全书约定：型号写"快照日期，以当时最新为准"
