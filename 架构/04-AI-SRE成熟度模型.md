# 第 14 章 · AI SRE 成熟度模型（L1-L5）

> 所属：第三部分 · 架构决策  ·  [← 返回目录](../README.md)

一个团队有共享网关、评估平台和自动发布，却无法复现上次灰度的版本组合。另一个团队只维护一个小服务，但任务要求、权限、发布和恢复都经过验证。谁的控制更可靠，不能从组件数量或公司规模判断。

第 11 章的 S/M/L 描述部署形态，第 13 章讨论具体选择。本章提供一套基于运行证据的自评工具，检查选择实施后是否持续受控。它是本书用于组织讨论的方法，不是经过行业统计校准的评级或认证。

---

## 1 · 先限定评估对象，再讨论级别

自评对象应是具体服务、任务范围和版本，说明流量、数据与授权边界。不能把一个低风险问答服务的结论直接推广到自动操作生产的 Agent，也不能用某个团队的历史成绩替代新系统验收。

这里的成熟度 L1—L5，与 Agent 自治 L0—L4、部署 S/M/L、评估投入 E1—E4 互不换算。成熟度较高不意味着应扩大自治；一个单上游服务也可以拥有经过演练的治理与退出能力。

| 级别 | 本章含义 | 主要证据问题 |
|---|---|---|
| L1 · 有边界的实验 | 知道在试什么，并限制实验影响 | 输入、权限、成本与负责人是否清楚？ |
| L2 · 生产可运行 | 已建立适用的服务承诺和恢复路径 | 用户依赖它时，失败是否可发现、可处理？ |
| L3 · 可重复交付与复用 | 控制不依赖临时操作或个人记忆 | 下一次变更、任务或接入能否重复执行？ |
| L4 · 可治理 | 风险、质量与资源决策形成闭环 | 证据是否真正影响发布、授权与改进？ |
| L5 · 可持续演进 | 依赖与人员变化时仍可验证承诺 | 替换、交接与退出是否在所需期限内可行？ |

级别表示逐步增强的控制证据，不规定必须先建共享平台或自管推理。哪些能力值得投入，应由实际服务风险和演进需要决定；没有依据声称所有组织的最佳终点都是 L3，或 L5 必须由大型矩阵团队实现。

---

## 2 · 五维判据：级别由证据支撑

五个维度是可观测、可靠性、安全、成本和组织。以下各级默认包含前一级中仍适用的要求。每项都需要指向当前版本、运行记录、测试或演练；写了文档只能证明设计意图。

### 可观测

| 级别 | 检查什么证据 |
|---|---|
| L1 | 能取得实验输入、版本、结果与用量；采集遵守数据边界 |
| L2 | 请求可关联，及时、完整与任务质量有适用测量，缺失可见 |
| L3 | 版本、分支、重试与评估结果可追溯，采集完整性有人维护 |
| L4 | 分桶覆盖与判定可信度持续检查，异常能进入决策和调查 |
| L5 | 新任务或依赖变化后，观测契约经验证更新，历史仍可解释 |

### 可靠性

| 级别 | 检查什么证据 |
|---|---|
| L1 | 超时、失败与重试有界，不无限占用实验资源 |
| L2 | 服务目标、接纳与降级规则明确，恢复入口已验证 |
| L3 | 发布清单与回归可重复，状态恢复、取消和副作用处理可演练 |
| L4 | 错误预算或风险信号影响发布，改进在独立任务上验证 |
| L5 | 关键依赖替换和退出演练满足业务需要，含容量与行为验证 |

### 安全

| 级别 | 检查什么证据 |
|---|---|
| L1 | 凭证、数据和实验权限有范围，未获授权的动作不可执行 |
| L2 | 实际数据流、身份与资源授权经检查，关键攻击路径有控制 |
| L3 | 新工具、上下文和渲染变化触发回归，越权与重复操作有测试 |
| L4 | 风险复核、例外批准与修复验证可追溯，挑战渠道有效 |
| L5 | 新攻击面和依赖变化能及时调整控制，旧权限与数据可清理 |

安全不是按"砍掉几条腿"累加分数。致命三角帮助检查数据外泄路径，不覆盖所有错误动作；白名单、沙箱或脱敏也都需要验证其适用范围。不能把某种特定技术，例如差分隐私，作为所有服务的统一成熟条件。

### 成本

| 级别 | 检查什么证据 |
|---|---|
| L1 | 知道用量、支出来源和实验上限 |
| L2 | 关键任务能归因，超限、重试和排队有预设处理 |
| L3 | 用量、配额与账单可核对，发布前可估计资源影响 |
| L4 | 单位有效任务成本与质量、容量、风险一起支持取舍 |
| L5 | 需求、单价、供给或部署变化后，成本假设能够重新验证 |

### 组织

| 级别 | 检查什么证据 |
|---|---|
| L1 | 有明确负责人、维护时间和求助路径 |
| L2 | 端到端服务责任、值班、停止和升级权限落实到人 |
| L3 | 发布、数据、授权与质量的分工可交接，有合格备份 |
| L4 | 独立挑战、风险例外与跨团队修复机制经实际验证 |
| L5 | 关键人员或团队变化后，通过交接演练继续履行承诺 |

组织能力不由是否开某个例会、评估向谁汇报或员工人数直接决定。表中检查的是机制及其实际效果。

---

## 3 · 先检查不能被总分抵消的缺口

生产范围内必要的授权和数据边界尚未验证，高风险动作无法限制或确认，或者服务失败没有可执行的处置路径，都需要先限制相应上线或自治范围。可观测、成本等维度的优点不能抵消这些缺口。

这与"还没使用某种平台"不同。检查需要说明：缺了哪项必要控制、哪条路径会受影响、当前缓解是什么、谁在什么条件下批准例外。不能只凭一个级别或工具名称宣布可上线。

未知也要单列。没有演练过的恢复路径，不应直接记录为失败，但不能作为已具备恢复能力的证据。非适用项则说明理由及重新变为适用的触发条件，例如尚未接入写工具；不能把未测试项都填为 N/A。

---

## 4 · 自评方法：画出能力差距，保留证据

先选定范围与评估日期，再逐维记录已满足的最高连续级别。每项附上证据位置、负责人、验证日期、运行条件和剩余未知。新增的高等级能力不能跳过仍适用的基础要求。

例如，一个服务的结果为：可观测 L3、可靠性 L2、安全 L2、成本 L3、组织 L2。若需要一个整体标签，只能说它在所有适用维度共同满足 L2；更有用的报告仍然是这张画像及其缺口，不能把五个数字平均成 L2.4。

| 维度 | 已证实级别 | 决定下一步的缺口 | 所需证据 |
|---|---|---|---|
| 可观测 | L3 | 长任务抽样不足 | 分桶覆盖与判定复核 |
| 可靠性 | L2 | 提交后恢复未演练 | 响应丢失和重启回放 |
| 安全 | L2 | 新工单通道未检查 | 接收方与内容授权测试 |
| 成本 | L3 | 降级的质量代价未知 | 同任务成本与结果对照 |
| 组织 | L2 | 发布人员无备份 | 非作者接手发布与恢复 |

这份示例不能据此批准尚未验证的新工单通道或写操作。画像描述的是有证据支持的范围，新的缺口可能要求缩小这个范围。

### 30 项证据提问清单

下面每维六问，用于发现遗漏，不相加定档。每题可以标注"已验证、仅设计、待验证、非适用"，并附证据。问题数量不代表权重，关键缺口需要独立处理。

**可观测**：

- [ ] 一次任务能关联到输入范围、模型与配置版本吗？
- [ ] 失败、取消、截断和未完成请求都能被看见吗？
- [ ] 关键任务桶有质量证据和样本量说明吗？
- [ ] 能区分排队、推理、工具和传输问题吗？
- [ ] 评估能追溯到原任务、证据和判定版本吗？
- [ ] 采集缺失、访问权限和保留期限有人检查吗？

**可靠性**：

- [ ] 服务目标和分母是否对应用户任务？
- [ ] 接纳、排队、重试与循环是否有界？
- [ ] 发布清单记录了模型、prompt、embedding、judge 等适用依赖吗？
- [ ] 旧版本与必要制品是否仍可用于恢复？
- [ ] 取消、检查点恢复及结果未知的动作是否演练过？
- [ ] 改进是否在完整链路与代表性负载上复验？

**安全**：

- [ ] 身份、租户、资源与动作授权由可信执行端检查吗？
- [ ] 不受信输入到私有数据和外发路径是否已分析？
- [ ] 新工具、渲染和跨 Agent 交接会触发检查吗？
- [ ] 审批是否绑定具体对象、参数和有效条件？
- [ ] 对抗测试发现的问题是否有处置与验证记录？
- [ ] 敏感内容、凭证、长期记忆和日志是否有数据边界？

**成本**：

- [ ] 能把用量与支出归到相应服务或任务吗？
- [ ] 重试、并发和外部操作是否纳入预算？
- [ ] 配额超限时的停止或降级行为经过验证吗？
- [ ] 单位成本是否同时说明有效完成率与负载？
- [ ] 自管、外部供给与迁移成本假设能复算吗？
- [ ] 质量、资源和风险取舍是否有获授权负责人？

**组织**：

- [ ] 服务责任与实际决策权限是否匹配？
- [ ] 关键工作的执行、批准、协商和通知是否清楚？
- [ ] 发布与风险判断是否有有效的独立挑战渠道？
- [ ] 值班能调用停止、恢复和专业升级路径吗？
- [ ] 关键岗位是否有备份并做过交接验证？
- [ ] 未决风险和例外是否有负责人、期限与重审条件？

## 5 · 识别有工具、没有控制的情况

评审时，要求展示一次实际执行，而非只看截图或配置：

- **有 SLO，未参与决定**：查看一次目标失守后的行动，或用演练验证政策；没有发生过事故不等于没有能力。
- **有 Eval，没有可信结论**：检查抽样、标签、漏放和缺失处理，确认发布用的是哪个评估版本。
- **有回滚按钮，恢复条件不齐**：实际切回旧组合，核对配置传播、容量、数据兼容和在途副作用。
- **有飞轮，未验证改进**：追溯一项真实问题如何复核、修复与复验，而非要求每月必须产生若干模型变更。
- **有独立团队，风险无人处理**：查看挑战与例外如何决定、修复如何关闭；部门名称不足以证明独立性。
- **声称可替换，未做迁移验证**：核对样本、容量、接口、数据和人员接手，而非限定所有组件必须 30 天内迁完。

这些检查既可能暴露设计缺口，也可能暴露证据缺口。处理办法不同：前者要补机制，后者要取得能够支持或推翻声明的验证结果。

---

## 6 · 把自评结果变成改进计划

先修与当前业务风险直接相关的缺口，再考虑复用和自动化收益。每项改进写明负责人、验收证据、资源与完成条件；不要为了多勾几项，优先建设容易展示但无关紧要的工具。

定期回顾可以纳入季度评审，但新任务、新工具、部署变化、重大事故和组织交接都应触发相关部分重评。旧画像保留范围与日期，便于区分系统进步、业务变化和判据调整。

本章最终产出是有证据的能力画像、关键缺口及下一步验证计划。第 15 章会继续检查一个维度容易忽略的问题：当前选择运行得越久，未来改变它的能力是否仍然存在。
