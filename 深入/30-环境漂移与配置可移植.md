# 深入 30 · 环境漂移：同一套系统换个环境为什么就变了

> [← 深入索引](../README.md)

---

## 0. 谁需要读这一篇

同一份代码、同一个 prompt，在你的笔记本上跑得好好的：引用准、格式对、该拒答的拒答。部署到客户内网（或另一个 region、另一个租户）之后，行为悄悄变了——引用开始飘、偶尔冒出多余的解释、某类请求答得比 demo 时差。但你没改一行代码，dashboard 全绿，延迟正常，请求数正常。

这不是模型"坏了"，是**环境不一样**。同一套系统搬到另一个环境，行为跟着变——本篇把这个现象叫**环境漂移**。它是[第 5 章 · 静默降级](../知识/05-AI推理服务的可靠性工程.md)那条"仪表全绿、质量偷偷掉"的孪生兄弟，只是根因换了一维。

如果你在做前置部署 / 驻场交付（把方案交到客户环境）、多租户 SaaS、或跨区域部署，这一篇是给你的。

---

## 1. 两个维度的漂移：时间维 vs 空间维

[前言](../00-前言.md)那句脊梁话说，在没有完整规格的 AI 系统里，你守护的不再是"对规格的偏离"，而是"行为的漂移"。漂移有两个方向，症状一样、根因不同：

| 维度 | 什么在变 | 典型触发 | 本书落点 |
|---|---|---|---|
| **时间维** | 同一个环境，行为随时间变 | 上游模型静默升级、数值/kernel 出错 | [静默降级](../知识/05-AI推理服务的可靠性工程.md)、[事故模式库](10-AI系统事故模式库.md) Pattern 1/3 |
| **空间维** | 同一个时刻，换个环境就变 | 两个环境的配置从一开始就不一样 | 本篇 |

两者的共同症状是同一个：**行为变了，可用性 / 延迟 / 请求数三条传统指标全绿**。所以时间维那套"eval 不会发现 production 已经烂了"的教训，原样适用于空间维——**你在自己环境里测得再好，也不代表客户环境里是对的**。

差别在根因。时间维的根因是"变了"（升级、精度 bug）；空间维的根因是"本来就不一样"——两个环境的模型别名、采样参数、检索库、限流从 day 0 就分叉，只是你一直在最干净的那个环境里测试，没看见。

---

## 2. 哪些东西换环境会悄悄变

环境漂移之所以难防，是因为"变量"藏在你通常不会写进代码、也不会进 code review 的地方。下面这张清单，是同一套系统跨环境最常见的分叉面：

- **模型别名 vs 快照版本**：`gpt-4o` / `claude-sonnet` 这类**别名**在不同环境、不同时间指向的**具体快照**可能不同。staging 指到的和客户 prod 指到的，未必是同一个。
- **采样参数默认值**：temperature、top_p、max_tokens 的默认值会随 SDK 版本、网关配置、控制台设置而变。一处没显式写死，就吃了别人的默认。
- **检索库 / 知识库版本**：RAG 的语料在客户环境里可能是另一份、或者是过期的一份。代码一样，召回的文档不一样，答案就不一样。
- **可用的模型档位**：某些区域 / 某些客户合约下，你 demo 用的旗舰模型根本调不到，被迫降级到次优模型。
- **上下文窗口与限流**：不同环境的 context 上限、rate limit、并发配额不同——demo 里能塞进去的长上下文，客户环境里被截断。
- **平台注入的 system prompt**：有些网关 / 平台会在你的 prompt 前面偷偷拼一段自己的前言，改变模型行为。
- **可用的工具 / MCP server**：Agent 能调到的工具集在客户环境里可能少一半，某些能力静默失效。
- **自托管量化**：客户在自己机房跑的是量化版模型，精度低于你 demo 用的全精度版（机理见[科学 03 · Quantization 为什么有时坏](../科学/03-Quantization为什么有时坏.md)）。
- **语言与 locale 分布**：客户真实流量的语言、编码、格式和你的测试样本不同，触发不同的 tokenization 行为（见[科学 04 · Tokenization 的坑](../科学/04-Tokenization的坑.md)）。
- **依赖版本**：SDK、tokenizer、模板引擎的版本差异，也会让同一段代码产出不同结果。

这些项的共同点：**它们都不在你的业务代码里，所以 code review 看不见、单元测试测不出**。

---

## 3. 为什么它比时间维更难抓

时间维的漂移至少有个**时点**——上游某天升级了、某次发布改了 kernel，你能对着时间线找。空间维没有时点：差异从第一天就静静存在，不触发任何变更事件，也就不触发任何告警。

更糟的是一个结构性偏差：**你几乎总在最干净的环境里测试**。demo 环境、staging 环境是你亲手搭的、配置最整齐的；客户环境、生产环境是最脏的、你最没法完全掌控的。于是"在我这能跑"（works on my machine）这句老话，有了一个 AI 版本——只不过传统软件"在我这能跑"通常会在别处直接报错、崩溃，好歹响；AI 的环境漂移**不会报错**，它照样返回 200、照样流畅，只是悄悄变差。

---

## 4. 怎么抓：给环境做奇偶校验

对付空间维漂移，核心动作是**环境奇偶校验**（environment parity）——把"两个环境到底哪里不一样"从猜测变成可比对的事实。四件事：

1. **配置即代码**：把 §2 清单里的每一项——模型快照（不是别名）、采样参数、检索库版本、限流、注入的 prompt、工具集——**显式写死、纳入版本控制**。凡是"吃默认值"的地方，都是一个潜在的跨环境分叉点。
2. **黄金脚本回放**（golden transcript replay）：备一组固定的输入样本，在**每个环境**各跑一遍，比对输出。这是 [canary eval](../知识/05-AI推理服务的可靠性工程.md) 的空间版——canary 沿**时间**探（同环境、定期探质量），parity replay 沿**环境**探（同时刻、跨环境比行为）。两个方向都要有。
3. **把 parity 当上线门槛**：新环境 / 新租户 / 新区域上线前，必须过一遍黄金脚本回放，而不只是过单元测试和冒烟测试。单元测试测的是代码，parity 测的是"这个环境的配置和基准环境一致"。
4. **trace 带环境指纹**（env fingerprint）：每条 trace 记下模型快照、采样参数、检索库版本、区域、SDK 版本。出了跨环境事故，能一眼比对两个环境的指纹差在哪，而不是靠人肉回忆"客户那边好像配置不一样"。

一句话：**时间维靠 canary 沿时间探，空间维靠 parity 沿环境探；两条探针缺一个，对应方向的漂移就是盲区。**

## 5. 三类高发场景

环境漂移在下面三类部署形态里最常见——它们的共同点是"一套系统要面对多个环境"：

- **前置部署 / 驻场交付**：把方案从 demo 交到客户环境，是最典型的一次性大落差。交付前用 parity replay 把 demo 环境和客户环境对齐一遍，比上线后救火便宜得多。移交时这份 parity 结果本身就该进[交接清单](../架构/07-与外部世界的契约.md)。
- **多租户 SaaS**：每个租户的配置（模型档位、检索库、限流、自定义 prompt）可能被单独覆盖。一个租户的"配置漂了"不该靠客户投诉才发现。
- **多区域部署**：区域路由可能把请求送到不同的模型档位或数据副本。"同一个功能在 A 区好、B 区差"往往就是区域间的模型 / 语料分叉。

---

## 6. 反模式

- **拿"在我这能跑"当验收标准**：demo 环境通过 ≠ 客户环境可靠。demo 环境是你能造出的最干净环境，恰恰最不能代表生产。
- **只有单元测试、没有 parity replay**：单元测试保证代码逻辑对，管不了"这个环境的模型 / 配置和基准一致"。
- **配置散在环境变量和控制台里、不进版本控制**：无法 diff 两个环境，也就无法定位漂移；出事只能靠人肉回忆。
- **客户环境不跑 canary eval**：以为"上线时测过"就行——但那是在**你的**环境测的，客户环境的质量从没被持续探过。
- **trace 不带环境指纹**：跨环境事故发生时，没有字段可比对，排障退化成猜。
- **用别名不锁快照**：全环境都写 `gpt-4o`，以为"都一样"，实际各环境指向的快照可能不同——这同时是空间维（环境间不同）和时间维（别名随时间滚动）的漂移入口。

---

## 7. 产出物 · 环境奇偶校验清单

交付 / 上线一个新环境时，应该能产出：

1. 一张**跨环境配置分叉清单**（按 §2）——逐项标注"这一项在各环境是否显式锁定、当前取值"。
2. 每个环境的**环境指纹**记录（模型快照 + 采样参数 + 检索库版本 + 区域 + 关键依赖版本）。
3. **黄金脚本回放结果**——基准环境与目标环境的输出比对，作为新环境上线门槛。
4. trace 里**带上环境指纹字段**的证明（跨环境事故可比对）。
5. 面向客户 / 接手团队的移交里，附上以上 parity 结果（对接[第 17 章 · 与外部世界的契约](../架构/07-与外部世界的契约.md)的交接清单）。

> [!WARNING]
> **何时这条不再适用**：当你的部署收敛到**单一托管环境**——纯 SaaS、单区域、无自托管、无多租户配置覆盖、全链路配置即代码且各环境共用同一份——空间维漂移的风险趋近于零，本篇退化为"上线时的一次性环境对齐检查"。但只要你还向**多个环境或多个客户**交付同一套系统，环境漂移就是一项持续义务，而不是一次性任务。另一个反向触发：当模型供应商提供**跨环境可验证的版本固定**（同一快照 ID 在所有区域 / 租户保证逐位一致）时，§2 里"模型别名 vs 快照"这一项的排查可以简化——但采样参数、检索库、注入 prompt 这些**你自己这侧**的分叉面依然要查。
