### TL;DR（6 句话）

1. **先定任务，再定 effort**：thinking 是计算预算的一部分；默认值与可关闭性按型号核验，不能从模型线名称推断。
2. **窗口上限不等于有效上下文**：历史 RULER 结果提示长文本会退化；当前型号要按证据检索与回答质量重测，不把旧模型的有效长度外推。
3. **用量榜要记时间窗与免费档**：本轮 OpenRouter 数据截至 2026-10-16，见 §1.5；流量不是业务质量，也不是直连 API 的版本保证。
4. **工具版本要分发布轨道**：CLI、IDE 扩展和 Desktop 的版本不能互换，当前 GitHub 数据见 §4.1。
5. **推理基建分开看显存链与性能链**：vLLM / SGLang 的 PD 解耦、prefix caching 是手段，是否获益仍由压测与 SLO 决定。
6. **缓存是独立计费契约**：当前 OpenAI 新代际有写入溢价，Anthropic 读价按型号变化，Gemini Argon 仅隐式，DeepSeek 别名可能换权重；见 §2.3 与 §3。

## 第一部分 · 技术流行趋势（2025-2026）

> 以下是观察维度与历史背景。任务、模型、执行器和评估条件改变时，需要重新验证，不能假定趋势只会深化。

### 1.1 Scaling 的转向：从参数到"推理时计算"

预训练计算与推理时计算是不同的投入维度。增加推理预算可以作为实验选项，但质量不保证随思考 token 单调提高；应在相同任务上比较结果、延迟与费用。

| 代表 | 机制 | 来源 |
|---|---|---|
| **OpenAI o1 / o3 / o4 series** | RL 训练的 chain-of-thought；训练时 + 推理时**双轴** scaling | 《Learning to Reason with LLMs》(2024-09)[^o1] |
| **DeepSeek-R1** | 研究强化学习与推理能力，并提供蒸馏路线；不同实验的训练阶段与数据条件不能混写 | arXiv 2501.12948 / Nature 2025[^r1] |
| **Claude Extended Thinking** | 每请求可配置思考 token 预算（budget_tokens），输出前有独立 thinking phase；Claude 4 起对外仅暴露 summarized thinking | Anthropic docs[^ext] |
| **Gemini 3 Deep Think** | Gemini 3.1 Pro 的"思考"模式 | Google AI Studio 2026 |

#### SRE 架构师必须内化的三件事

1. **Reasoning token 的计费和 usage 归类要按模型文档核验**（例如 OpenAI 的 `output_tokens_details.reasoning_tokens`、Anthropic 的思考 token、Gemini 的 thought token 字段）——预算按实测占比和当前价格计算，不预设 3–10 倍放大。
2. **Thinking 阶段是否可流式、摘要字段叫什么都按 API 契约核验**——各家模型的流事件、摘要开关和默认值可能不同；UI 不能假定一定有摘要或一定会持续输出。
3. **对延迟敏感的场景先做对照评估**；复杂推理是否开启 thinking，应由质量收益、延迟和成本的实测权衡决定。

### 1.2 MoE 成为主流架构

**MoE（Mixture of Experts）**：模型参数量大，但每次推理只激活一小部分。好处是"大而不贵"。

2025-2026 主流 MoE 产品：

| 模型 | 总参 | 激活参 | 备注 |
|---|---|---|---|
| DeepSeek V3 / V4 | 685B / 1T+ | ~37B | 开源 MoE 标杆[^ds] |
| Llama 4 Maverick | 400B+ | ~17B | Meta 首个全 MoE 旗舰[^llama4] |
| Qwen 3.6-35B-A3B | 35B | 3B | 阿里 MoE 代表[^qwen] |
| Gemini / Claude / GPT 等闭源产品 | 按具体型号的官方披露核验 | - | 未披露时不据性能或传闻推定 MoE |

#### 对推理基建的含义

- **Expert Parallel (EP)** 成为部署 MoE 的第三种并行（除 TP/PP 外）
- **Routing imbalance** 是新故障模式（某些 expert 被过度路由 → 热点 GPU）
- **显存估算变复杂**：激活参数主要影响每 token 计算；常规驻留部署仍要容纳全部权重（按 EP / TP 分片）+ KV cache + 运行时开销，不能用激活参数量代替权重显存

### 1.3 上下文长度的军备竞赛与"有效长度"幻觉

#### 宣称值 vs 实际可用

历史 RULER 研究[^ruler]提醒我们：支持某个输入窗口，不等于在该长度内能稳定检索、整合和推理。受测模型与协议有时间边界，不能拿历史结果给当前全部型号指定一个"有效长度"。

| 要核对的对象 | 验证方法 | 容易混淆的结论 |
|---|---|---|
| 接口窗口与输出限制 | 查所用型号的输入、输出与共享窗口契约 | 能接收不代表能正确利用 |
| 证据检索与整合 | 同任务比较位置、干扰、跨文档关系与引用支持性 | 单针测试不等于开放任务质量 |
| 完整任务代价 | 记录排队、prefill、缓存、生成和失败重做 | 输入更长不必然按同一比例变慢 |

长上下文、检索、重排和压缩应在同一任务上比较。具体型号上限见 §3；机制与测量边界见[深入 01](01-首包延迟与吞吐的影响因素.md)和[Lost in the Middle](../科学/02-Lost-in-the-Middle.md)。

### 1.4 Agentic 能力：从 "补全" 到 "长任务"

任务委托扩大后，评估对象需要包含模型、执行器、工具、状态和反馈。一次连续运行数小时的成功案例，不能直接证明同类任务都能可靠自动完成。

[METR 的 time-horizon 说明](https://metr.org/time-horizons/)按人类专家完成任务的时长刻画难度，并指定成功概率；它不是 AI 连续运行多久的指标，也不是生产 SLO。该页面已注明不再持续更新，不应当成当月模型排名。

#### Agentic 重要基准（SRE 都该知道）

| 基准 | 评估对象 | 比较时保留的条件 |
|---|---|---|
| SWE-bench Verified | 代码问题解决的完整系统 | 数据子集、harness release、工具、预算与测试 |
| GAIA[^gaia] | 多步通用助理任务 | 数据划分、工具、尝试次数与验收标准 |
| OSWorld[^osworld] | 桌面交互任务 | 数据集版本、动作与时间预算、人类基线协议 |
| τ-bench 系列[^tau] | 工具与多轮交互 | 具体基准版本、任务、用户模拟与成功判定 |
| Vending-Bench / Project Vend[^vend] | 长时程决策或实际试验 | 模拟与真实部署的边界、资源及运营条件 |

这些对象不能混成同一个成功率，也不能跨版本用"超过人类"概括。榜单与来源状态见 §3.11。

<a id="关键质变点"></a>

#### 长任务需要同时管理进度、状态与恢复

[Anthropic 的长任务案例](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)用环境初始化、增量工作和交接材料连接多次会话。这是特定工程方案，适用时要验证进度记录是否真实、未完成状态是否可定位，以及恢复是否重复外部动作。

把任务持续运行与可恢复运行分开验收：记录任务 ID、输入与策略版本、已完成动作、检查点、停止原因和接手条件。摘要或重启本身不能保证这些状态得到保存。

### 1.6 推理基础设施的三个关键演化

下面是可实验的实现方向，不是所有部署都应启用的默认项：

1. **PD 解耦**：比较 prefill / decode 负载、资源利用与跨池传输，验证端到端 SLO 与故障恢复；不同硬件的局部吞吐提升不能直接外推。
2. **Prefix caching**：测量可复用前缀、命中、驱逐、租户隔离与读写计费；复用低或缓存压力高时，收益可能不足以覆盖成本。
3. **Speculative decoding**：按目标模型、候选接受率、并发和额外资源比较完整任务吞吐，不能把单请求加速倍数直接换算成省钱比例。

版本核验见 §4.5；容量与机制见[深入 05](05-LLM推理服务的容量规划.md)和[深入 20](20-单卡装不下的大模型分布式推理.md)。

### 1.7 AI 编码工具：从 "补全" 到 "Agent"

局部补全、对话编辑、任务委托与异步交付可以并存。采用哪一种，要看任务边界、权限、验证与恢复条件，不是按年份必须升级的阶段。

| 工作形态 | 主要验收对象 | 增加的工程问题 |
|---|---|---|
| 局部补全与对话编辑 | 代码或建议在当前上下文中是否成立 | 局部测试与资料来源 |
| 完整任务委托 | 目标、约束、变更与测试是否满足要求 | 任务预算、工具权限与副作用 |
| 异步和跨会话工作 | 接手者能否还原进度、复查证据并恢复 | 持久状态、取消、重复执行和交接 |
| 多路径协作 | 分工与合并是否提升任务结果 | 共因错误、协调代价与责任归属 |

Skills、Hooks、Subagents 是实现手段；是否采用取决于本方证据。更多 Agent 或更长运行，不自动意味着工作更有效。

### 1.8 2025-2026 其他重要趋势（速扫）

本轮把观察重点放在**执行状态与上下文分离**。[Managed Agents 工程说明](https://www.anthropic.com/engineering/managed-agents)展示了会话日志、harness 与沙箱解耦的一种做法：保存完整事件与选择本次上下文是不同职责。它提供了可恢复状态设计的案例，不能替代本方对权限、日志完整性和副作用的验证。

另一个重点是**验证器本身的证据**：长任务的最终画面正确，仍可能完成了相似却错误的指令。评估应检查原始要求、过程中发生的动作和约束，而不只看最后的输出。具体研究与边界见 §2.5。

## 第二部分 · 工程最佳实践

> 场景、候选与验证问题共同构成选型起点。工作方式或任务条件变化时，结构本身也要重审。

### 2.1 选型总原则

> **先定义任务与约束，再用有判定依据的样本比较完整方案。** 小样本可以排查明显问题，但不是生产准入的统一门槛。

三条原则（具体型号与当前价格查 §3；下表是待 eval 的候选，不代表本轮重新跑过业务测试）：

1. **多源对照**：LM Arena（主观）+ SWE-bench（硬指标）+ OpenRouter（用量）+ 你的小样本
2. **比较有效完成的总成本**：先排除不满足质量、数据或权限条件的方案，再比较单价、重试、验证与维护；没有通用的 70% 流量分配
3. **对任务用 Thinking，对速度用非 Thinking**：thinking 可能是同一模型的运行模式，也可能是独立型号；按官方参数与实际延迟分别评估

### 2.2 八大场景最佳实践

> [!NOTE]
> 下列型号是待评估候选，不是固定胜者。区分能力补充与控制职责：前者需要测量净收益，后者需要落实责任与验证。一个组件可能同时承担两者，不能按名称决定永久保留或全部删除。参见[第 13 章](../架构/03-架构师的决策框架.md)。

#### 场景 A · 代码生成与重构

| 子场景 | 首选 | 备选 | 自托管 |
|---|---|---|---|
| 大仓库 agentic 编码 | **Claude Opus / Fable** / Claude Sonnet | GPT 旗舰 / Codex 可用型号 | DeepSeek V4 Pro / Qwen3.6-35B |
| 日常补全 | Claude Sonnet / Gemini Flash | GPT 轻量档 | DeepSeek Flash |
| 算法/竞赛难题 | Claude Opus / Fable / o4 / GPT 高 effort 档 | Grok reasoning | Hermes 4-405B |

**需要按任务核实的考虑**：

- 核对项目说明、代码与任务上下文是否准确、及时且可追溯，不把单个文件名当作成功保证
- 工具执行器独立检查身份、资源、参数和授权范围；是否逐次确认按已批准策略和操作风险决定
- 比较压缩、检索、交接和保持上下文的实际结果；清空或重启前验证状态与证据可恢复
- 生成器与评审器分别做任务评估；评审器价格或厂商不同，不保证其能发现关键错误

#### 场景 B · SRE 运维诊断

| 子任务 | 首选 | 理由 |
|---|---|---|
| 长日志 / trace 分析 | **Gemini 推理旗舰** / Claude Sonnet | 先验证长文本证据召回与真实费用 |
| 结构化字段抽取（事件摘要）| Claude Haiku / Gemini Flash-Lite | 便宜、延迟低 |
| 事故根因推理 | Claude Opus / Fable / GPT 高 effort 档 | Thinking 值得多付 |
| 工单自动分类 | Claude Haiku / DeepSeek Flash | 高吞吐批处理 |

**关键考虑**：

- **Tool use 必须白名单**（见[第 6 章](../知识/06-AI自治与上下文架构约束.md) 致命三角）
- **强制引用日志来源**（每个结论附原日志行号）
- 比较直接分析与结构化中间结果；后者便于校验，也可能丢失线索或引入抽取错误
- **RAG 你的 runbook**：通用模型不知道你家环境，必须喂

#### 场景 C · RAG 与知识问答

| 子场景 | 首选 |
|---|---|
| 大文档单次总结（合同、报告）| Gemini 推理旗舰（1M context + 单次便宜）|
| 中小文档 + 高质量答案 | Claude Sonnet |
| 高频问答（成本敏感）| Claude Haiku / Gemini Flash-Lite |
| 自托管 | Qwen 3.6 / Llama 4 Scout |

**关键考虑**：

- **固定文档放前面** → 有机会提高 prompt caching 命中；节省比例取决于命中率、读写价格和供应商契约（见[深入 02](02-Prompt-Caching原理.md)）
- 核查引用是否支持结论；仅要求附链接，不能保证回答有依据
- 按文档结构和任务比较切分、重叠与候选数量，不把固定片长当作通用最优值
- **Embedding 用专用模型**（bge-m3 / E5 / Cohere Embed），不要用主力模型做 embedding
- 是否加入 Rerank、候选数量和 Top-k 由召回质量、延迟预算与任务 eval 决定；可从检索 Top-50 → Rerank Top-5 作为实验起点

#### 场景 D · 结构化数据抽取

| 子场景 | 首选 |
|---|---|
| 高吞吐（日百万条）| Claude Haiku / Gemini Flash-Lite / DeepSeek Flash |
| 复杂嵌套 schema | Claude Sonnet |
| 多语言（中英混合）| Qwen 3.6 |

**关键考虑**：

- **用厂商的 Structured Output / JSON Schema 强制约束**，不要靠 prompt 让它"输出 JSON"
- **Temperature = 0 或 0.1**——仅限仍接受采样参数的非推理型号；新模型的参数支持与默认值逐个核验，不从 Sonnet / Haiku / GPT 等家族名称推断。确定性还须依靠 Structured Output、约束与 eval。
- **永远做 eval**：准确率目标（不是 100%）+ 漂移监控
- 失败材料经授权检查、去标识、抽样、标注和复核后进入评估集，见[第 8 章](../知识/07-质量可观测性与DataFlywheel.md)

#### 场景 E · 复杂推理 / 规划 / 数学

| 子场景 | 首选 |
|---|---|
| 多步推理 | **Claude Opus / Fable** / OpenAI o4 / GPT 旗舰 High |
| 数学 | 同上 + DeepSeek-R1 distilled |
| 代码推理（边想边写）| Claude Opus / Fable |

**关键考虑**：

- **按模型实际支持开启 extended thinking / reasoning mode**；预算按实测的 reasoning/thinking token 和端到端延迟计算，不预设固定倍数
- **流式 UI 和思考摘要要按 API 契约逐项核验**——不同模型对摘要字段、流事件和是否强制流式的规定不同
- **把 reasoning/thinking token 单独记入 usage**，按当前模型的计费规则核算，并监控其在总输出中的占比；放大倍数应从持续样本测得
- **Fallback 到非 thinking 版本**：对简单 query 自动降级

#### 场景 F · 视觉理解

| 子场景 | 首选 |
|---|---|
| 通用图像理解 | Gemini 推理旗舰 / GPT 多模态档 / Claude Sonnet |
| OCR | Gemini 推理旗舰 / Qwen 3.5 Omni |
| 截图理解（UI / 仪表盘）| Claude Opus / GPT 多模态档 |

**关键考虑**：

- **图像分辨率决定上限**——太小会漏
- 对照直接视觉推理与先描述后推理，检查文字化过程是否丢失关键视觉证据
- **多图累积成本**——每张图都占 token

#### 场景 G · 长任务 Agent

**候选**：Claude Opus / Fable / Sonnet，以及 Codex 当前可用的 GPT 档位；具体型号与预算见 §3。长任务仍须用自己的持续执行样本验证。

**关键考虑（比模型选择更重要）**：

- **上下文工程**：compaction 策略、subagent 隔离、外部记忆 `NOTES.md` 模式
- 检查点记录已完成、在途与未知动作；恢复时验证幂等和副作用，不能只恢复一段文本
- 记录必要证据与版本，并按权限和保留策略管理；离线回放与重新调用工具分别验收
- **预算上限**：token + 时长；跑飞了自动停

### 2.3 Prompt Caching 使用策略

当负载存在可复用前缀时，值得比较的优化手段。[深入 02](02-Prompt-Caching原理.md) 详述原理，这里只讲最佳实践。

#### 厂商缓存对比（2026-10-16 核验 🕒）

| 平台 | 触发 | 写成本 | 读成本 | 保留 / 限制 |
|---|---|---|---|---|
| Anthropic | `cache_control`，显式断点 / 自动模式 | 5min 为 1.25×；1h 为 2× | Opus/Sonnet 5.5 为 0.05×；Fable 5.1 为 0.025×；Haiku 5.5 为 0.1× | 按型号查最小前缀；命中续期 |
| OpenAI GPT-5.6+ | 默认隐式，也支持显式断点 | **1.25×，不是零溢价** | GPT-6.1 Sol 为 0.05×；Astra/Luna 为 0.1× | 最小 1024 token；新配置见深入 02 |
| Google Gemini | 隐式 / 部分型号支持显式资源 | 按模型与接口计价 | Argon 为 0.05×；3.8 Flash 为 0.1× | **Argon 只支持隐式缓存** |
| DeepSeek Flash | 自动 | 按实际命中分类计费 | 见 §3.7 的分时价表 | 计价不承诺每次命中 |

来源：[Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing)、[OpenAI caching](https://developers.openai.com/api/docs/guides/prompt-caching)、[Gemini pricing](https://ai.google.dev/gemini-api/docs/pricing)、[DeepSeek pricing](https://api-docs.deepseek.com/quick_start/pricing)。各类 token 按对应费率计算，缓存写价不再叠加一次普通输入价。

#### 落地清单

- ✅ **固定内容放前面**：系统提示 → 参考文档 → 用户当前请求
- ✅ **用户 ID / 时间戳 / session ID 放后面或省略**
- ✅ **版本号变更 = 全体缓存失效**，灰度时预留成本冲击预算
- ✅ **路由亲和**（自建服务）：同 session 到同实例
- ✅ **监控 cache hit rate**：突降 20% 立即排查
- ❌ **别以为 "cache_control" 加了就一定命中**——监控真实命中率

### 2.4 成本优化四板斧

1. **路由**：按任务质量和完整成本决定候选分流，实测路由器的误分与额外开销。
2. **Caching**：按命中、读写与驱逐计费核算净收益，见 2.3。
3. **Batch**：核验具体接口的折扣、工具与缓存计价、排队及过期重试，见[深入 13](13-离线批量推理.md)。
4. **推理优化**：按负载比较推测解码等实现，同时计入额外设备与维护成本。

### 2.5 可观测性与 Eval 最佳实践

> Trace、评估与生产监控通过任务和版本标识关联。原始 Trace 不等于已标注的评估集，存储与服务也可以分开部署；处理流程见[第 8 章](../知识/07-质量可观测性与DataFlywheel.md)。

<a id="eval"></a>
<a id="三层-eval-体系"></a>

#### 评估职责的三种视角

```text
L1 Assertion（硬规则）
  ├─ 字段存在性 / 类型 / 长度
  ├─ 必要格式（JSON valid? URL 有效?）
  └─ 黑名单词（PII / 脏话 / 竞品名）

L2 Judge 模型评分
  ├─ 用 LLM 给输出打分（relevance / faithfulness / correctness）
  ├─ 必须定期校准：sample 100 条让人打分，计算 judge-human 一致性（Cohen's κ）
  └─ κ < 0.6 → 作为示例触发人工复核；结合类别分布、置信区间和误差代价校准阈值（见[深入 06](06-Eval-Pipeline设计.md)），再决定是否换 judge 或改 rubric

L3 A/B 测试 / 用户反馈
  ├─ 线上分流
  ├─ 收集 thumbs up/down、编辑距离、留存率
  └─ 补充真实使用信号，但满意度、留存与任务正确性不是同一指标
```

[AgentHorizon](https://arxiv.org/abs/2610.11050)（2026-10-08，预印本）用相近但不兼容的指令构造负例，检查 judge 是否真能核实长轨迹的完成条件。其结果提示应分别检查正确轨迹的接受与失败轨迹的拒绝；本轮只核对论文摘要，未复现实验，不将其分数外推成本方生产能力。

#### Evals 自身的 SLO

- **Eval 覆盖率**（生产样本有多少被 eval pipeline 评估）
- **Eval 延迟**（样本到 eval 结果的时间）
- **Judge-human 对齐度**（不对齐 = eval 失效）
- **Eval pipeline uptime**（evals 挂了你就瞎了）

完整内容见[第 6 章](../知识/06-AI自治与上下文架构约束.md)。**极简版**：

```text
Lethal Trifecta（私有数据访问 + 不受信输入 + 外泄通道）
  → 工具访问是放大器：同时加宽不受信输入的入口和外泄的出口，但不是独立的一条腿
  → 在可信执行端验证并阻断可利用路径，应用授权与基础设施控制配合

```

### 2.7 工具使用反模式清单（务必避免）

- 仅靠 Prompt 约束授权、格式或事实，缺少实际执行与内容验证。
- 不核对型号契约，就复制 temperature、thinking、streaming 或缓存参数。
- 把上下文越长、更多 Agent、更多 verifier 当成普遍更可靠。
- 只比较单次调用价，不计重试、工具、评审、返工和状态恢复。
- 用同一批题反复调优，再声称分数证明泛化；或把原始 Trace 自动变成 gold set。
- 发现验证器放过关键错误后，仍以总通过率高为理由扩大权限。

## 第五部分 · 选型决策 7 步流程

下面是组织评审的一种顺序，具体深度和样本由任务与风险决定：

1. **定义任务和结果**：明确成功完成、错误放行、安全停止及业务损失。
2. **列出硬约束**：数据、权限、时限、可接受损失与必须满足的合同条件。
3. **记录比较维度**：质量、端到端延迟、总成本、容量、运维与退出代价。
4. **选取可行候选**：可以从现有单路径开始，不强制凑齐三家或一种自管部署。
5. **做有依据的对照**：用获准样本，保留独立检验集，覆盖任务与关键负例；披露样本量与未知。
6. **隔离与受控发布**：影子流量避免重复副作用；灰度窗口、流量和阈值按所需证据设计。
7. **决定扩大、维持、缩小或撤回**：记录负责人、实际恢复证据和触发重审的条件。

小样本测试可以排除明显问题，不能替代长尾覆盖与生产准入。当前公共榜单也不能替你验证具体业务，详见[第 13 章](../架构/03-架构师的决策框架.md)。
