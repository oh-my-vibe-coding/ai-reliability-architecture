### TL;DR（6 句话）

1. **先定任务，再定 effort**：thinking 是计算预算的一部分；默认值与可关闭性按型号核验，不能从模型线名称推断。
2. **窗口上限不等于有效上下文**：历史 RULER 结果提示长文本会退化；当前型号要按证据检索与回答质量重测，不把旧模型的有效长度外推。
3. **用量榜要记时间窗与免费档**：本轮 OpenRouter 数据截至 2026-10-15，见 §1.5；流量不是业务质量，也不是直连 API 的版本保证。
4. **工具版本要分发布轨道**：CLI、IDE 扩展和 Desktop 的版本不能互换，当前 GitHub 数据见 §4.1。
5. **推理基建分开看显存链与性能链**：vLLM / SGLang 的 PD 解耦、prefix caching 是手段，是否获益仍由压测与 SLO 决定。
6. **缓存是独立计费契约**：当前 OpenAI 新代际有写入溢价，Anthropic 读价按型号变化，Gemini Argon 仅隐式，DeepSeek 别名可能换权重；见 §2.3 与 §3。

## 第一部分 · 技术流行趋势（2025-2026）

> **稳定部分**。这些趋势 1-2 年内不会推翻，只会深化。具体数字随时间漂移。

### 1.1 Scaling 的转向：从参数到"推理时计算"

**旧范式**：预训练投入越大 → 模型越强（Kaplan / Chinchilla scaling laws）。
**2024-2026 新范式**：**test-time compute** 成为第二条 scaling 曲线——**让模型在推理时"多想一会"**，质量随"思考 token 数"继续提升。

| 代表 | 机制 | 来源 |
|---|---|---|
| **OpenAI o1 / o3 / o4 series** | RL 训练的 chain-of-thought；训练时 + 推理时**双轴** scaling | 《Learning to Reason with LLMs》(2024-09)[^o1] |
| **DeepSeek-R1** | 纯 RL（无人工标注 reasoning traces）涌现自反思 / 自验证；可蒸馏到小模型 | arXiv 2501.12948 / Nature 2025[^r1] |
| **Claude Extended Thinking** | 每请求可配置思考 token 预算（budget_tokens），输出前有独立 thinking phase；Claude 4 起对外仅暴露 summarized thinking | Anthropic docs[^ext] |
| **Gemini 3 Deep Think** | Gemini 3.1 Pro 的"思考"模式 | Google AI Studio 2026 |

#### SRE 架构师必须内化的三件事

1. **Reasoning token 的计费和 usage 归类要按模型文档核验**（例如 OpenAI 的 `output_tokens_details.reasoning_tokens`、Anthropic 的思考 token、Gemini 的 thought token 字段）——预算按实测占比和当前价格计算，不预设 3–10 倍放大。
2. **Thinking 阶段是否可流式、摘要字段叫什么都按 API 契约核验**——各家模型的流事件、摘要开关和默认值可能不同；UI 不能假定一定有摘要或一定会持续输出。
3. **对延迟敏感的场景先做对照评估**；复杂推理是否开启 thinking，应由质量收益、延迟和成本的实测权衡决定。

### 1.2 MoE 成为主流架构

**MoE（Mixture of Experts）**：模型参数量大，但每次推理只激活一小部分。好处是"大而不贵"。

2025-2026 主流 MoE 产品：

| 模型 | 总参 | 激活参 | 备注 |
|---|---|---|---|
| DeepSeek V3 / V4 | 685B / 1T+ | ~37B | 开源 MoE 标杆[^ds] |
| Llama 4 Maverick | 400B+ | ~17B | Meta 首个全 MoE 旗舰[^llama4] |
| Qwen 3.6-35B-A3B | 35B | 3B | 阿里 MoE 代表[^qwen] |
| Gemini / Claude / GPT-5 | 未公开 | - | 普遍推测为 MoE |

#### 对推理基建的含义

- **Expert Parallel (EP)** 成为部署 MoE 的第三种并行（除 TP/PP 外）
- **Routing imbalance** 是新故障模式（某些 expert 被过度路由 → 热点 GPU）
- **显存估算变复杂**：激活参数主要影响每 token 计算；常规驻留部署仍要容纳全部权重（按 EP / TP 分片）+ KV cache + 运行时开销，不能用激活参数量代替权重显存

### 1.3 上下文长度的军备竞赛与"有效长度"幻觉

#### 宣称值 vs 实际可用

| 模型 | 宣称 | RULER / NIAH 实测有效 | 来源 |
|---|---|---|---|
| Gemini 1.5 Pro | 1M | **>128K**（好于平均）| RULER[^ruler] |
| Llama 3.1 70B | 128K | **~64K** | RULER[^ruler] |
| GPT-4 (1106) | 128K | **~64K** | RULER[^ruler] |
| Llama 4 Maverick | **10M** | 未见 RULER 公开结果 | [未验证] |
| Claude Sonnet 4.5 (1M 版) | 1M | 1M 版 SWE-bench 78.2% vs 200K 版 77.2%——**只差 1 个点**[^sonnet45] | Anthropic |

> [!IMPORTANT]
> **SRE 要知道**：RULER 核心发现——"宣称 ≥32K 的模型，只有**一半**能在 32K 长度下有效工作"[^ruler]。不要把"标称 context 大 = 能用"当真。

#### 实用推论

- **超过 128K 就要验证你的场景**。单个"needle in haystack"通过 ≠ 复杂多针任务通过。
- **Chunking + Rerank 与整段长 context 要做同任务对照**；跨文档关系推理和局部检索的最优路径可能不同。
- 长 context 会增加输入账单与 prefill 工作量；全注意力、稀疏注意力和缓存命中的耗时曲线不同，不用 token 数线性外推 TTFT（见[深入 01](01-首包延迟与吞吐的影响因素.md)）。

### 1.4 Agentic 能力：从 "补全" 到 "长任务"

#### 关键质变点

- **Tool use 可靠性提升**：τ-bench 2024 年论文基线只有 airline 46% / retail 69%（Claude 3.5 Sonnet）；2026 年前沿模型已到 ~95%+（τ-bench / Vending-bench）[^tau]
- **Long-running tasks**：Anthropic Project Vend 让 Claude Sonnet 3.7 运营自动贩卖机数周[^vend]；Claude Code / Codex CLI 能连续工作数小时
- **Computer use / Browser use**：OSWorld 基准（真实桌面任务）2024-04 论文发布时最佳模型仅 12.24%、人类 72.36%[^osworld]；2026-06 快照下 OSWorld-Verified 头部已 ~85%（Claude Fable 5 等研究分支），GPT-5.4 也在 2026-03 报出 75%——均已反超人类基线。两年内从 12% 到反超人类，是 agentic 能力兑现最快的赛道

#### Agentic 重要基准（SRE 都该知道）

| 基准 | 评估什么 | 论文基线 → 当前状态（2026-06 快照）| 来源 |
|---|---|---|---|
| **SWE-bench Verified** | 真实 GitHub issue 修复 | 当前 SOTA：Claude 4.5 Opus 76.80%（mini-SWE-agent 口径，2026-02 提交；全局含 agent 系统口径 79.20%，详见 3.11 节）| [^swe] |
| **GAIA** | 通用助理（多步推理+工具）| 快照缺失 | [^gaia] |
| **OSWorld** | 桌面 computer use | 2024 论文基线 12.24% → OSWorld-Verified 头部 ~85%（2026-06），已超人类 72.36% | [^osworld] |
| **τ-bench** | Tool use + 多轮对话 | 2024 论文基线：Claude 3.5 Sonnet airline 46% / retail 69% → 2026 前沿 ~95%+；已出 τ³-bench | [^tau] |
| **Vending-Bench** | 长时程商业决策 | Anthropic Project Vend 公开 | [^vend] |

### 1.6 推理基础设施的三个关键演化

1. **Disaggregated Serving（PD 解耦）成为一等公民**
   - Prefill 和 Decode 分到不同 GPU pool（前者需要算力，后者需要带宽）
   - vLLM V1 / SGLang 0.5 都已原生支持；SGLang 报告 GB200 上 decode 吞吐提升 **2.7×**[^sg]
   - 完整机制（含 DeepSeek-671B 端到端算例）见 [深入 20 · 分布式推理](20-单卡装不下的大模型分布式推理.md)
2. **Prefix Caching 从可选变强制**
   - vLLM 的 Automatic Prefix Caching、SGLang 的 RadixAttention
   - 不开启就是白付钱（RAG / 长系统提示场景成本可降 80%+）
3. **Speculative Decoding 商品化**
   - EAGLE / DFlash / n-gram / suffix 多种方法集成
   - 单请求 tokens/s 可 2-4× 提升

### 1.8 2025-2026 其他重要趋势（速扫）

- **多模态原生（Multimodal Native）**：Gemini 3.1、GPT-5.4、Claude Opus 4.7、Meta Muse Spark 都是从训练第一天就 multimodal；"文本+图像"不再是后接的 vision adapter[^muse]

## 第二部分 · 工程最佳实践

> **稳定部分**。场景-首选-关键考虑的三层结构，模型名可以换，结构不变。

### 2.1 选型总原则

> **不要被榜单牵着走。先定义场景，再列约束，再做你自己的 20 条样本 eval。**

三条原则（具体型号与当前价格查 §3；下表是待 eval 的候选，不代表本轮重新跑过业务测试）：

1. **多源对照**：LM Arena（主观）+ SWE-bench（硬指标）+ OpenRouter（用量）+ 你的小样本
2. **先廉后贵**：便宜模型能解决就别上旗舰；`Claude Haiku / Gemini Flash / DeepSeek Flash` 覆盖 70% 日常任务
3. **对任务用 Thinking，对速度用非 Thinking**：thinking 可能是同一模型的运行模式，也可能是独立型号；按官方参数与实际延迟分别评估

### 2.2 八大场景最佳实践

> [!NOTE]
> 下面每个场景的"关键考虑"混着两类、寿命不同：**结构级**（白名单、强制引用、prompt caching、eval——不随模型变）和**技巧级**（哄模型的编排小动作，如"先结构化再推理""先 describe 再 reason"——能力脚手架，模型能力一代代变强后收益趋零）。两类的"过期"方式不同：换型号名是型号级漂移，技巧作废是能力级漂移——月度换名时别漏了后者。判据见 [第 13 章 · §1 两种脚手架](../架构/03-架构师的决策框架.md)。

#### 场景 A · 代码生成与重构

| 子场景 | 首选 | 备选 | 自托管 |
|---|---|---|---|
| 大仓库 agentic 编码 | **Claude Opus / Fable** / Claude Sonnet | GPT 旗舰 / Codex 可用型号 | DeepSeek V4 Pro / Qwen3.6-35B |
| 日常补全 | Claude Sonnet / Gemini Flash | GPT 轻量档 | DeepSeek Flash |
| 算法/竞赛难题 | Claude Opus / Fable / o4 / GPT 高 effort 档 | Grok reasoning | Hermes 4-405B |

**关键考虑（不随模型变）**：

- **项目上下文文件** (`CLAUDE.md` / `AGENTS.md`) 是命中率的决定因素
- **Tool use 白名单**（只读命令默认；变更类动作强制 confirm）
- **Context 定期压缩**：长对话用 `/clear` 或 subagent 重启，比硬撑 1M 有效
- **双模型分层**：生成用贵模型，code review 用便宜模型

#### 场景 B · SRE 运维诊断

| 子任务 | 首选 | 理由 |
|---|---|---|
| 长日志 / trace 分析 | **Gemini 推理旗舰** / Claude Sonnet | 先验证长文本证据召回与真实费用 |
| 结构化字段抽取（事件摘要）| Claude Haiku / Gemini Flash-Lite | 便宜、延迟低 |
| 事故根因推理 | Claude Opus / Fable / GPT 高 effort 档 | Thinking 值得多付 |
| 工单自动分类 | Claude Haiku / DeepSeek Flash | 高吞吐批处理 |

**关键考虑**：

- **Tool use 必须白名单**（见[第 6 章](../知识/06-AI自治与上下文架构约束.md) 致命三角）
- **强制引用日志来源**（每个结论附原日志行号）
- **先结构化再推理**：让模型先抽取字段成 JSON → 再基于 JSON 推理（比直接"分析日志"准得多）——能力脚手架，模型直读长文推理变强后收益趋零
- **RAG 你的 runbook**：通用模型不知道你家环境，必须喂

#### 场景 C · RAG 与知识问答

| 子场景 | 首选 |
|---|---|
| 大文档单次总结（合同、报告）| Gemini 推理旗舰（1M context + 单次便宜）|
| 中小文档 + 高质量答案 | Claude Sonnet |
| 高频问答（成本敏感）| Claude Haiku / Gemini Flash-Lite |
| 自托管 | Qwen 3.6 / Llama 4 Scout |

**关键考虑**：

- **固定文档放前面** → 有机会提高 prompt caching 命中；节省比例取决于命中率、读写价格和供应商契约（见[深入 02](02-Prompt-Caching原理.md)）
- **强制引用来源**——对抗幻觉的底层护栏
- **Chunking 小而重叠**：500-800 token / 片，相邻重叠 10-20%
- **Embedding 用专用模型**（bge-m3 / E5 / Cohere Embed），不要用主力模型做 embedding
- 是否加入 Rerank、候选数量和 Top-k 由召回质量、延迟预算与任务 eval 决定；可从检索 Top-50 → Rerank Top-5 作为实验起点

#### 场景 D · 结构化数据抽取

| 子场景 | 首选 |
|---|---|
| 高吞吐（日百万条）| Claude Haiku / Gemini Flash-Lite / DeepSeek Flash |
| 复杂嵌套 schema | Claude Sonnet |
| 多语言（中英混合）| Qwen 3.6 |

**关键考虑**：

- **用厂商的 Structured Output / JSON Schema 强制约束**，不要靠 prompt 让它"输出 JSON"
- **Temperature = 0 或 0.1**——仅限仍接受采样参数的非推理型号；新模型的参数支持与默认值逐个核验，不从 Sonnet / Haiku / GPT 等家族名称推断。确定性还须依靠 Structured Output、约束与 eval。
- **永远做 eval**：准确率目标（不是 100%）+ 漂移监控
- **失败样本自动回收做下一轮 eval 数据**（data flywheel，见[第 8 章](../知识/07-质量可观测性与DataFlywheel.md)）

#### 场景 E · 复杂推理 / 规划 / 数学

| 子场景 | 首选 |
|---|---|
| 多步推理 | **Claude Opus / Fable** / OpenAI o4 / GPT 旗舰 High |
| 数学 | 同上 + DeepSeek-R1 distilled |
| 代码推理（边想边写）| Claude Opus / Fable |

**关键考虑**：

- **按模型实际支持开启 extended thinking / reasoning mode**；预算按实测的 reasoning/thinking token 和端到端延迟计算，不预设固定倍数
- **流式 UI 和思考摘要要按 API 契约逐项核验**——不同模型对摘要字段、流事件和是否强制流式的规定不同
- **把 reasoning/thinking token 单独记入 usage**，按当前模型的计费规则核算，并监控其在总输出中的占比；放大倍数应从持续样本测得
- **Fallback 到非 thinking 版本**：对简单 query 自动降级

#### 场景 F · 视觉理解

| 子场景 | 首选 |
|---|---|
| 通用图像理解 | Gemini 推理旗舰 / GPT 多模态档 / Claude Sonnet |
| OCR | Gemini 推理旗舰 / Qwen 3.5 Omni |
| 截图理解（UI / 仪表盘）| Claude Opus / GPT 多模态档 |

**关键考虑**：

- **图像分辨率决定上限**——太小会漏
- **先 describe 再 reason**：让模型先描述图像，再基于描述推理——能力脚手架，原生多模态变强后可省
- **多图累积成本**——每张图都占 token

#### 场景 G · 长任务 Agent

**关键考虑（比模型选择更重要）**：

- **上下文工程**：compaction 策略、subagent 隔离、外部记忆 `NOTES.md` 模式
- **Checkpoint**：Agent crash 后能从中间继续
- **全审计日志**：所有 tool 调用必须可回放
- **预算上限**：token + 时长；跑飞了自动停

| 规模 | 推荐 |
|---|---|
| 单 H100 / 消费卡 | Qwen 3.6-27B / Llama 4 Scout / Mistral Small 4 |
| 多卡 | Llama 4 Maverick / DeepSeek V4 Pro / Qwen 3.6-35B MoE / Hermes 4-405B |

- **Tool use / Structured output 支持度差异大**，先验证再选型
- **运维成本**往往比 GPU 成本更贵（人力 + 值班）

### 2.3 Prompt Caching 使用策略

**单一最强的成本优化手段**。[深入 02](02-Prompt-Caching原理.md) 详述原理，这里只讲最佳实践。

#### 厂商缓存对比（2026-10-16 核验 🕒）

| 平台 | 触发 | 写成本 | 读成本 | 保留 / 限制 |
|---|---|---|---|---|
| Anthropic | `cache_control`，显式断点 / 自动模式 | 5min 为 1.25×；1h 为 2× | Opus/Sonnet 5.5 为 0.05×；Fable 5.1 为 0.025×；Haiku 5.5 为 0.1× | 按型号查最小前缀；命中续期 |
| OpenAI GPT-5.6+ | 默认隐式，也支持显式断点 | **1.25×，不是零溢价** | GPT-6.1 Sol 为 0.05×；Astra/Luna 为 0.1× | 最小 1024 token；新配置见深入 02 |
| Google Gemini | 隐式 / 部分型号支持显式资源 | 按模型与接口计价 | Argon 为 0.05×；3.8 Flash 为 0.1× | **Argon 只支持隐式缓存** |
| DeepSeek Flash | 自动 | 按实际命中分类计费 | 见 §3.7 的分时价表 | 计价不承诺每次命中 |

来源：[Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing)、[OpenAI caching](https://developers.openai.com/api/docs/guides/prompt-caching)、[Gemini pricing](https://ai.google.dev/gemini-api/docs/pricing)、[DeepSeek pricing](https://api-docs.deepseek.com/quick_start/pricing)。各类 token 按对应费率计算，缓存写价不再叠加一次普通输入价。

#### 落地清单

- ✅ **固定内容放前面**：系统提示 → 参考文档 → 用户当前请求
- ✅ **用户 ID / 时间戳 / session ID 放后面或省略**
- ✅ **版本号变更 = 全体缓存失效**，灰度时预留成本冲击预算
- ✅ **路由亲和**（自建服务）：同 session 到同实例
- ✅ **监控 cache hit rate**：突降 20% 立即排查
- ❌ **别以为 "cache_control" 加了就一定命中**——监控真实命中率

### 2.4 成本优化四板斧

1. **分层**：70% 流量 → 便宜模型（Haiku / Flash-Lite / DeepSeek V4 Flash）；剩 30% → 旗舰
2. **Caching**：见 2.3，RAG / 长系统提示场景能省 80%+
3. **Batch API**：非实时场景（离线抽取、定期报告）→ **OpenAI / Anthropic Batch 折扣 50%**
4. **Speculative decoding**（自建服务时）：2-4× tokens/s 提升，成本相应下降

### 2.5 可观测性与 Eval 最佳实践

> **核心洞察（重复但必须反复强调）**：Traces = Eval Dataset = 生产监控。一套系统，不是两套。

#### 三层 Eval 体系

```
L1 Assertion（硬规则）
  ├─ 字段存在性 / 类型 / 长度
  ├─ 必要格式（JSON valid? URL 有效?）
  └─ 黑名单词（PII / 脏话 / 竞品名）

L2 Judge 模型评分
  ├─ 用 LLM 给输出打分（relevance / faithfulness / correctness）
  ├─ 必须定期校准：sample 100 条让人打分，计算 judge-human 一致性（Cohen's κ）
  └─ κ < 0.6 → 作为示例触发人工复核；结合类别分布、置信区间和误差代价校准阈值（见[深入 06](06-Eval-Pipeline设计.md)），再决定是否换 judge 或改 rubric

L3 A/B 测试 / 用户反馈
  ├─ 线上分流
  ├─ 收集 thumbs up/down、编辑距离、留存率
  └─ 权威最高，但样本慢
```

#### Evals 自身的 SLO

- **Eval 覆盖率**（生产样本有多少被 eval pipeline 评估）
- **Eval 延迟**（样本到 eval 结果的时间）
- **Judge-human 对齐度**（不对齐 = eval 失效）
- **Eval pipeline uptime**（evals 挂了你就瞎了）

### 2.6 安全与自治边界（极简提示）

完整内容见[第 6 章](../知识/06-AI自治与上下文架构约束.md)。**极简版**：

```
Lethal Trifecta（私有数据访问 + 不受信输入 + 外泄通道）
  → 工具访问是放大器：同时加宽不受信输入的入口和外泄的出口，但不是独立的一条腿
  → 在基础设施层砍掉一条腿（通常是"外泄通道"）
  → 沙箱 / egress 白名单 / capability-scoped 凭证
  → 禁止 Agent 修改自己的配置 / 凭证
```

### 2.7 工具使用反模式清单（**务必避免**）

- ❌ **用 prompt "请输出 JSON"**（要用 Structured Output / JSON Schema）
- ❌ **系统提示里放时间戳 / UUID**（缓存全部失效）
- ❌ **让 AI 操作生产 + 无白名单**（致命三角）
- ❌ **不做 eval 就上线**（你根本不知道它好不好）
- ❌ **不看模型代际就调 Temperature**——旧一代非推理模型做抽取/分类仍应压到 0-0.1；但 o 系 / GPT-5 系 / Anthropic 2026 旗舰传参直接 400，extended thinking 下温度只能是 1，Gemini 3 调低可能循环或降智
- ❌ **假定所有 Thinking API 都有同一种流式摘要**——先按所用模型的契约确认流事件、摘要字段和默认值，再设计等待提示与超时策略
- ❌ **长 context 硬塞**（效果差且贵，不如 RAG）
- ❌ **用通用 embedding 模型做特定领域 RAG**（精度差）
- ❌ **所有请求用同一个旗舰模型**（70% 任务是过度配置）
- ❌ **Prompt caching 标记了就不管**（必须监控命中率）

## 第五部分 · 选型决策 7 步流程

> **稳定部分**。任何时候遇到选型问题，走这 7 步。

```
1. 定义场景
   └─ 对应第二部分哪个子场景（A-H）？
   └─ 如果跨多个场景，拆开分别决策

2. 列出硬约束
   ├─ 数据敏感度 → 是否允许 API / 托管？
   ├─ 延迟要求 → p99 TTFT < 多少？
   ├─ 成本上限 → 每百万 token / 每请求预算
   ├─ 合规 → 必须 VPC / 必须某地域？
   └─ 可控性 → 是否需要固定模型版本？

3. 列出软约束
   ├─ 生态（tool use / structured output 支持度）
   ├─ 文档 / SDK 质量
   └─ 厂商稳定性（API breaking change 历史）

4. 短名单 3 个
   ├─ 闭源旗舰 1（Claude / GPT / Gemini 旗舰之一）
   ├─ 性价比档 1（Haiku / Flash / DeepSeek V4 Flash 之一）
   └─ 开源备选 1（Qwen / Llama / Mistral 之一）

5. 做你自己的 20-50 条样本 Eval
   ├─ 从生产取真实样本（必要时脱敏）
   ├─ 定义 pass / fail 标准
   ├─ 测三方：准确率 + 延迟 p50/p99 + 成本
   └─ 对照 LM Arena / SWE-bench 看方向是否一致

6. 小流量上线
   ├─ 影子流量（双跑，不影响用户）一周
   ├─ 然后 5% 真实流量一周
   └─ 观察：cache hit rate、质量漂移、成本、失败率

7. 决定扩量 or 回退
   ├─ 扩量：逐步 25% → 50% → 100%
   ├─ 回退：分析失败案例，回到第 3 步
   └─ 每次都留可回滚开关（feature flag）
```

**一条常见错误**：直接看榜单 Top 1 就上线。**你自己场景的 20 条样本 eval，权重高于任何公开榜单**。
